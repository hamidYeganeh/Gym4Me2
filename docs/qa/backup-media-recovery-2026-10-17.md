# بازیابی رسانه و استمرار حذف — ۱۷ اکتبر ۲۰۲۶

این برش نقص پوشش فایل‌های PH2 را رفع می‌کند و شاهد بازیابی **محلی و ایزوله** است؛ T029، PH1 و پذیرش staging کامل بسته نمی‌شوند.

## نقص و اصلاح

capture عملیاتی قبلاً فقط `club_media.object_key` را می‌خواند. تصویر خدمت، مدرک و تصویر گفتگو در dump وجود داشتند، اما فایل متناظرشان تضمین نمی‌شد. `scripts/backup-media.mjs` اکنون این چهار منبع را از همان تراکنش repeatable-read که snapshot مشترک `pg_dump` را صادر کرده می‌خواند. کلیدها یکتا هستند؛ پیام حذف‌شده و orphan فاقد ارجاع وارد capture نمی‌شوند. تصاویر نسخه‌های تاریخی خدمت حفظ می‌شوند. نبود object یا قطع stream باعث شکست capture پیش از ثبت بکاپ موفق می‌شود. schemaهای قدیمی فقط جدول‌های موجود را می‌خوانند.

مسیر مشترک `scripts/recovery-media.mjs` ابتدا manifest، همهٔ checksumها و دفتر حذف تازه را بررسی می‌کند، سپس replay واقعی را اجرا می‌کند و **پس از replay** ارجاع‌های دیتابیس بازیابی‌شده را می‌خواند. فقط فایل‌های هنوز مرجع‌دار بارگذاری می‌شوند. دفتر قدیمی، checksum خراب، فایل مرجع‌دار مفقود و شکست replay مانع بارگذاری‌اند. اعتبارسنجی فایل‌ها مالک/مجوز خصوصی، عدم symlink برای metadata و فایل‌ها و پوشهٔ objects، اندازه و قرارداد metadata را نیز بررسی می‌کند.

فرمان جدید `apps/api/scripts/restore-media.ts` همین مسیر را برای مقصد بازیابی محلی آفلاین اجرا می‌کند. مقصد به دیتابیس و bucket جدا با نام مشخص محدود است؛ bucket باید خالی باشد و اتصال دیگری به دیتابیس وجود نداشته باشد. این فرمان database را restore نمی‌کند و هیچ API یا ترافیکی را فعال نمی‌کند. تکمیل تنظیمات origin، URL فایل، نقش‌ها و پذیرش پیش از cutover هنوز لازم است. دستور prepare قدیمی اصلاح شد: فایل‌ها نباید پیش از replay بارگذاری شوند.

## staging و زمان‌بندی مشاهده‌شده

Docker در شروع برش سالم نبود. restart معمول Docker Desktop موفق شد؛ volumeهای موجود حفظ شدند. dependencies آزمون و staging محلی راه‌اندازی شدند. snapshot رمزگذاری‌شدهٔ پیش از migration، recovery verify و بررسی کامل دو مخزن موفق بودند. سپس migrationهای افزایشی staging اعمال شدند؛ `verify-staging.ts` مجوز DML را روی هر ۸۷ جدول عمومی و منع DDL، تاریخچهٔ migration و نقش‌های elevated تأیید کرد. snapshot پس از migration و recovery verify نیز موفق بودند؛ زمان snapshot نهایی `2026-10-17T05:47:39.158Z` است.

staging فعلی فاقد فایل مرجع‌دار بود: verify آن فقط یک dump و صفر حذف گزارش کرد. بنابراین شاهد پوشش رسانهٔ PH2، تمرین چهار فایل بالا است؛ بکاپ staging خالی شاهد فلو خرید یا بازیابی کاتالوگ پُر نیست.

`launchctl print gui/501/ir.gym4me.backup` سرویس موجود را running، PID برابر 30277، با keepalive/runatload نشان داد. هیچ worker تازه‌ای جایگزین آن نشد. state واقعی پس از بازیابی Docker: ledger موفق در `05:43:20.527Z` و snapshot موفق در `05:43:22.838Z`، هر دو با صفر شکست متوالی. موفقیت قدیمی check مربوط به ۱۳ اکتبر است؛ بررسی کامل دستی هر دو مخزن در این برش نیز موفق شد و state زمان‌بند دستکاری نشد. برنامهٔ موجود: دفتر هر ۵ دقیقه، snapshot روزانه و check هفتگی؛ failureها backoff دارند.

## کنترل‌ها و موارد باز

- ۹ آزمون capture/verify/recovery/scheduling موفق؛ این مجموعه شامل round-trip واقعی Restic و آزمون‌های خطای metadata/stream/replay است. کل مجموعهٔ اسکریپت عملیات همراه alert و association نیز با ۱۱ آزمون موفق اجرا شد؛ alert در این آزمون شبیه‌سازی شده بود و اعلان بیرونی واقعی ارسال نشد.
- TypeScript API و ESLint چهار entrypoint مرتبط موفق؛ ۵۹ فایل محافظت‌شدهٔ رابط بدون تغییر؛ `git diff --check` موفق.
- workflow CI با آزمون‌های جدید به‌روز شد؛ remote CI در این برش اجرا نشده است.
- هر دو مخزن تنظیم‌شده روی **همین میزبان** هستند. رمزگذاری و جدا بودن repository، استقلال از خرابی دیسک/میزبان را اثبات نمی‌کند. مقصد خارج از دستگاه، custody کلید، RPO/RTO واقعی، retention سیاست‌دار و تمرین روی میزبان مستقل همچنان بازند.
- bucket عمومی/رسانهٔ restore پیش از تأیید سیاست حذف نباید در دسترس قرار گیرد؛ این ابزار مقصد آفلاین می‌سازد/می‌پذیرد و انتشار ترافیک را انجام نمی‌دهد. دروازهٔ کامل انتشار و سناریوی از دست‌رفتن دفتر authoritative همچنان نیاز به پذیرش عملیاتی دارد.
- UI/native، اعلان بیرونی، کاتالوگ چندسازمانی staging، فروش واقعی و پایلوت با این نتیجه پذیرش نمی‌شوند.
