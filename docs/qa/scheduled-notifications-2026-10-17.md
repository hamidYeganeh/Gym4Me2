# یادآوری رزرو و پیشنهاد انتظار — ۱۷ اکتبر ۲۰۲۶

ادامهٔ T055، T056 و T060. چرخهٔ یادآوری با تغییر رزرو هماهنگ شد؛ این شاهد، پذیرش کامل این تسک‌ها یا PH0–PH2 نیست.

## رفتار نهایی

- زمان‌بندی مشترک `scheduleReservationReminders` بعد از خریدِ تأییدشده، تأیید میزبان و جابه‌جایی در همان تراکنش اجرا می‌شود. برای رزرو در انتظار تأیید یادآوری ساخته نمی‌شود. موعد با `greatest(now(), start_at - interval '1 hour')` خود PostgreSQL تعیین می‌شود؛ payload شناسهٔ سانس و کلید، revision رزرو را دارد.
- هر تغییر، کارهای قدیمی را حتی اگر worker قبلاً lease گرفته باشد بازنشسته می‌کند و فقط یک کار جاری نگه می‌دارد. برگشت A→B→A، کلید تازه دارد؛ کار پردازش‌شدهٔ A مانع یادآوری معتبر تازه نمی‌شود. replay همان فرمان، کار اضافه ایجاد نمی‌کند. شکست جابه‌جایی، رزرو و کار قبلی را حفظ می‌کند.
- تحویل یادآوری، scheduled بودن سانس، شروع در یک ساعت آینده، confirmed بودن رزرو، تطبیق سانس payload و پردازش‌نشده‌بودن همان کار را دوباره بررسی می‌کند. ترتیب قفل share سانس سپس رزرو، با مسیر جابه‌جایی/لغو میزبان هماهنگ است؛ بررسی حساب/ترجیح و insert در همان تراکنش انجام می‌شوند.
- لغو، حضور با QR، حضور دستی و غیبت خودکار، کارهای یادآوری و اعلان‌های **خوانده‌نشده**ٔ منسوخ را بازنشسته می‌کنند. read history حذف نمی‌شود. بنابراین اعلان ثبت‌شده درست پیش از لغو هم پس از تراکنش لغو به‌صورت unread باقی نمی‌ماند.
- پیشنهاد انتظار فقط وقتی تحویل می‌شود که status هنوز offered، مهلت پیشنهاد معتبر، سفارش awaiting_payment و مهلت آن معتبر باشد. قفل share پیشنهاد/سفارش با پذیرش و انصراف هماهنگ است. پذیرش، انصراف، انقضا و لغو سفارش، کار در صف و اعلان unread پیشنهاد را بازنشسته می‌کنند. پذیرش بستهٔ رایگان همچنان پرداخت بانکی یا برداشت خودکار ایجاد نمی‌کند.
- lookup بازنشستگی با شناسهٔ aggregate/kind و source_key دقیق گیرنده انجام می‌شود؛ indexهای aggregate/kind صف و order_id لیست انتظار افزوده شدند. این بررسی وجود index و رفتار را اثبات می‌کند، نه benchmark بار production.

## migration و قرارداد

`0030_sports_reminder_context` فقط یادآوری‌های قدیمیِ هنوز پردازش‌نشده را به سانس جاری رزرو و موعد دیتابیس متصل می‌کند و دو index را می‌سازد. سابقهٔ پردازش‌شده یا خوانده‌شده بازنویسی نمی‌شود. این backfill، تاریخچهٔ زمان‌بندیِ از‌دست‌رفتهٔ نسخه‌های قدیمی را بازسازی نمی‌کند. API عمومی یا قرارداد پول تغییر نکرد؛ تغییر در payload داخلی صف است.

**build تازه پیش از migrationهای 0029 و 0030 نباید روی staging راه‌اندازی شود.** هر دو migration هنوز در آن محیط بازند؛ آخرین snapshot تأییدشدهٔ staging مربوط به 0028 است.

## شواهد اجرای نهایی

آزمون‌ها و کامپایلرها ترتیبی اجرا شدند؛ PostgreSQL و S3 تست مستقیم پاسخ می‌دادند.

| `node --import tsx --test test/notification-delivery.integration.test.ts` | **۲۱/۲۱**، حدود ۳٫۲۰ ثانیه؛ `gym4me_scheduled_notification_guard_test` از schema تازه با migration نهایی |
| `jest --config test/jest.commerce.json --runInBand` | **۶۷/۶۷**، حدود ۶٫۴۳ ثانیه؛ `gym4me_scheduled_regression_test` از schema تازه و S3 محلی واقعی |
| API `tsc --noEmit` | موفق؛ شامل تست‌های تازه |

| `nest build` | موفق با سقف heap برابر ۷۶۸ MiB |
| migration و indexها | آخرین journal برابر `1791914419000` و هر دو index جدید در هر دو دیتابیس تأیید شدند |
| حفظ طراحی | ۵۹ فایل محافظت‌شده بدون تغییر؛ `git diff --check` موفق |

۱۳ آزمون جدیدِ مجموعهٔ اعلان، مسیر تأیید میزبان، موعد دقیق، زمان dispatch نامناسب، جابه‌جایی و replay، A→B→A، شکست جابه‌جایی، کار leaseشدهٔ کهنه، لغو، QR تکراری، غیبت، opt-out/replay، رقابت قفل لغو میزبان، چهار وضعیت پیشنهاد و backfill را پوشش می‌دهند. هشت آزمون قبلیِ حذف حساب/ترجیحات/ارسال هم‌زمان نیز در همین اجرای نهایی پاس‌اند.

رقابت لغو میزبان با SQL مسیر قفل سانس/رزرو و `cancelHostedOrder` اجرا شد؛ ابتدا تحویل پشت قفل حساب و سپس لغو پشت قفل تحویل واقعاً در `pg_blocking_pids` مشاهده شدند. این آزمون، شاهد هم‌زمانی سرویس است و آزمون مجوز HTTP تازه محسوب نمی‌شود. آزمون شصت‌وهفتم، `SportsOperationsService.manualAttendance` واقعیِ DI را اجرا می‌کند و حذف unread/جلوگیری از تحویل دیررس را اثبات می‌کند.

پس از cleanup، شمار users/organizations/services/reservations/messages/notifications/orders/outbox در هر دو دیتابیس هر هشت صفر تأیید شد. فقط همان دو namespace اختصاصی، پس از کنترل نبود اتصال، بدون FORCE حذف شدند. اجرای اولیهٔ ۲۰/۶۶ پیش از indexهای نهایی نیز موفق بود؛ نتیجهٔ جدول مربوط به اجرای دوبارهٔ schema نهایی و آزمون‌های افزوده است.

workflow موجود، مجموعهٔ اعلان را با نام روشن‌ترِ privacy/scheduling/obsolete work اجرا می‌کند؛ اجرای remote CI در این برش انجام نشده است. رابط تغییری نکرد و QA بصری یا دستگاه تازه ادعا نمی‌شود.

## موارد باز

یک ping محدودِ سه‌ثانیه‌ای control API Docker دوباره timeout شد؛ سلامت کنترل محیط برای migration/backup staging تأیید نشد. فضای میزبان حدود ۱٫۷ GiB بود؛ حداقل فضای runner native پایین آورده نشد. VM یا volume با زور حذف نشد.

T060 هنوز به بررسی رویدادهای غیرزمانیِ منسوخ، رقابت تغییر ترجیح در لحظهٔ تحویل، تحویل بیرونی و پذیرش UI/دستگاه نیاز دارد. T056 هم به پذیرش کامل واجدشرایط‌بودن، صف/ظرفیت و رابط انتظار نیاز دارد؛ این برش فقط چرخهٔ اعلان پیشنهاد را تقویت می‌کند. مدیریت گفتگوی بیزینس، سایر صفحات/عملیات و دروازه‌های PH0/PH1/PH2 همچنان طبق backlog بازند. فروش واقعی و پایلوت پذیرفته نشده‌اند.

ادامهٔ همین روز: اعلان‌های سفارش/استرداد و scope job مالی با ۳۱ آزمون اعلان و ۶۷ آزمون تجارت در [شاهد اعلان مالی](order-notifications-2026-10-17.md) تقویت و بررسی شدند؛ موارد باز دیگر همچنان برقرارند.
