# حرکت وب و بارگذاری مسیر — ۱۷ اکتبر ۲۰۲۶

این برش طبق انتخاب فعلی کاربر فقط وب است. Docker، PostgreSQL، staging، S3 و دستگاه اجرا نشدند. API عمومی fixture فقط GET/HEAD و داده مصنوعی داشت و هیچ فرم یا خریدی ارسال نشد. **پذیرش کامل حرکت، loading و PH0 انجام نشده است.**

## شاهد و تغییر

در تب آزمایش با prefers-reduced-motion=reduce، هنگام ورود سرد به support، boundary مقصد `/support` موجود بود ولی شمار main فعال صفر شد؛ ناوبری هنوز دیده می‌شد. snapshot و frame ثبت‌شده مشاهدات متوالی‌اند، نه یک timestamp مشترک. صفحه سپس درست نمایش داده شد؛ طول فضای خالی اندازه‌گیری نشد. [دادهٔ قبل و بعد](motion-web-2026-10-17.json).

۲۶ صفحهٔ جدید `<Suspense>` بدون fallback داشتند. `components/luma/page-loading.tsx` اضافه شد: main دارای نام بارگذاری، متن role=status و چهار Skeleton تزئینیِ aria-hidden با توکن موجود و `motion-reduce:animate-none`. کنترل یا دادهٔ ساختگی قابل کلیک به صفحه اضافه نشده است. همهٔ آن ۲۶ boundary اکنون این fallback را دارند.

برای بارگیری خود کد مسیر، ۱۵ بخش جدید نیز `loading.tsx` دارند که فقط همان کامپوننت را re-export می‌کند. مسیرهای discovery/club، کارت club/coach و وابستگی‌های محافظت‌شده تغییر نکردند؛ loading ریشهٔ app ساخته نشد. CSS عمومی، Kit و زمان‌های حرکت عوض نشده‌اند. فهرست دقیق فایل‌ها و hashها در manifest است. guard۵۹ فایل محافظت‌شده پاس شد.

مستندات نصب‌شدهٔ Next16.4 دربارهٔ loading.js و useSearchParams مبنای کار بودند. [راهنمای رسمی loading](https://nextjs.org/docs/app/api-reference/file-conventions/loading) توضیح می‌دهد fallback مسیر برای streaming است و دادهٔ uncached در layout می‌تواند نمایش آن را به تأخیر بیندازد؛ تغییرات scoped هستند و ادعای رفع همهٔ منابع تأخیر layout نمی‌شود. [راهنمای رسمی Skeleton](https://ui.shadcn.com/docs/components/base/skeleton) نیز خوانده و کامپوننت نصب‌شده استفاده شد. فرمان installed CLI `pnpm exec shadcn docs skeleton` بدون خروجی ماند و با SIGINT متوقف شد؛ dependency یا preset نصب/بازنویسی نشد.

## مشاهدهٔ reduced-motion و بازگشت

در مرورگر، رسانهٔ reduce واقعاً true بود. در نمونه‌های جزئیات خدمت، checkout، برگشت به جزئیات، برگشت به فهرست، جست‌وجو، گفتگو، خانه و فهرست نهایی، main فعال یکی بود و transform/filter مرز صفحه none و opacity=1 بودند. blur ناوبری none و خود ناوبری بیرون boundary حرکت بود. این‌ها snapshotهای مشاهده‌شده‌اند، نه ثبت همهٔ فریم‌ها یا اثبات زمان صفر در تمام مسیرها. نسخهٔ نهایی نیز روی `/services` با reduce=true، RTL، فارسی/تیره و۳۹۰×۸۴۴ یک main و ناوبری بدون blur داشت.

Back دومِ فوری در یک فراخوانی به guard برخورد کرد؛ انتظار اولیهٔ ابزار برای searchbox تمام شد و snapshot مقصد را همچنان جزئیات نشان داد. پس از فاصلهٔ عادی، Back به فهرست رسید. این مورد با guard موجود جلوگیری از دو پرش سریع سازگار است؛ به‌عنوان خرابی Router یا پذیرش لمس سخت‌افزاری ثبت نشد. جست‌وجو همان شناسهٔ `/services` را نگه داشت.

شبیه‌سازی CDP دو بار برای تب‌های آزمایش انجام و موفق شد، اما به‌جای timeout درخواستی۳۰۰۰ms، فراخوانی‌ها حدود۱۸۸ و۶۲۷ ثانیه طول کشیدند؛ حتی نگه‌داشتن Promise در REPL از مسدودشدن ابزار جلوگیری نکرد. درخواست دوم فقط پس از مشاهدهٔ done=true/result بدون خطا ادامه یافت. این بخش از ابزار برای ادامهٔ این هدف تکرار نمی‌شود. هیچ تنظیم OS یا تب کاربر تغییر نکرد؛ تب شبیه‌سازی‌شده در پایان بسته شد.

## آزمون کندی و محدودیت مشاهده

پروکسی QA فقط‌خواندنیِ loopback روی7382، Next روی7381 را جلو می‌گذاشت. ابتدا کد support/messages را۱۵۰۰ms و سپس services/checkout را نیز۵۰۰۰ms به تأخیر انداخت؛ فقط مسیر فایل static در log بود، نه Cookie، query یا بدنه. تمام نوشتن‌ها405 بودند. این script در `.artifacts` است و جزو اپ محصول نیست.

سه انتظار برای visible شدن PageLoading موفق نشدند: یک بار فقط fallback داخلی، بار دوم پس از loadingهای segment و بار سوم در reduce با تأخیر۵ثانیه. صفحهٔ نهایی هر بار بارگذاری شد؛ این نتیجه **پذیرش بصری fallback یا اثبات نبود فریم خالی نیست**. فراخوانی آخر حدود۵۱ثانیه زمان دیواری ابزار داشت؛ مشاهدهٔ حالت‌های کوتاه با این مسیر قابل اتکا نبود. مشاهدهٔ مجدد در محیط مرورگر با ابزار پایدار، و در صورت نیاز رفع علت نمایش‌ندادن fallback، باز می‌ماند. screenshot ساختگی از loading تهیه نشد.

## اعتبارسنجی و ادامه

ESLint کامپوننت و۴۱ فایل route موفق شد؛ اجرای اول از root بدون eslint.config رد شد و با cwd صحیح application دوباره پاس شد، بدون خاموش‌کردن قواعد. build نهایی ورزشکار با heap۵۱۲MiB، یک worker و Webpack cache خاموش موفق شد: compile۸٫۹s، TypeScript۱٫۶۳۷s و۶۴ صفحه. `git diff --check` پاس است. ساخت هم‌زمان دیگری یا native اجرا نشد.

زمان‌های پیکربندی‌شدهٔ fade۱۸۰، push۳۰۰ و sheet۳۲۰ms طبق برنامه حفظ شدند؛ این‌ها اندازه‌گیری حرکت Luma نیستند. راهنمای transitions-polish برای تطبیق کاربرد خوانده شد و صرفاً برای نزدیک‌شدن به توکن عمومی، عددی عوض نشد. mapping فرم‌های ورود/پروفایل که هنوز fallback fade/push دارند باید با تصمیم Sheet برنامهٔ مصوب تطبیق نهایی شود. اندازه‌گیری زمان، جهت و بازگشت همهٔ حرکت‌ها، anchor باشگاه با دادهٔ واقعی، reduced-motion صفحه‌خوان/دستگاه و پذیرش کامل loading بازند.

در پایان viewport reset شد، تب‌های آزمایش بسته شدند و proxy، preview۲۵۶MiB و fixture۹۶MiB با SIGINT عادی خاتمه یافتند. پروکسی heap۶۴MiB داشت و هیچ compiler هم‌زمان با آن‌ها اجرا نشد.
