# مدارک ورزشکار در وب — ۱۸ اکتبر ۲۰۲۶

این برش طبق محدودیت فعلی کاربر فقط وب است. Docker، PostgreSQL، S3، staging و native اجرا/تغییر داده نشدند. هیچ مدرک واقعی، رضایت، سفارش یا فرمِ دارای فایل ارسال نشد. فایل‌های chooser مصنوعی بودند و فقط انتخاب/اعتبارسنجی شدند؛ کلیک ارسال بدون فایل نیز فقط برای آزمون اعتبارسنجی مرورگر بود. PH0/PH1/PH2 و T068 بسته نمی‌شوند.

## یافته و اصلاح

در نسخهٔ قبل، برای service۲ با نیاز «گواهی آمادگی ورزشی»، فهرست خصوصیِ مصنوعی یک مدرکِ service۱ داشت. در UI هیچ پیام خالی برای service۲ دیده نمی‌شد؛ snapshot و DOM قبل، فرم۱ و emptyMessages=[] را ثبت کردند. شرط خالی اکنون روی لیستِ فیلترشده محاسبه می‌شود.

فرم بارگذاری پیش‌تر مستقل از موفقیت خواندن خصوصی رندر می‌شد. اکنون QueryState خصوصی کل فرم/تاریخچه را می‌پوشاند؛401 لینک ورود با returnTo شامل service و503 خطای Retry دارد و در هر دو حالت file input صفر است. این کنترل UX است؛ مجوز واقعی از AuthGuard/ConsentGuard سرور می‌آید و در این برش بازآزمایی نشده است.

برای خدمتِ بدون requirement، select خالی و فرم غیرقابل‌استفاده حذف شد و پیام روشن جای آن است. Form با service کلید می‌خورد، نام فایل و خطا state محلی دارند و ورودی‌ها در ارسال غیرفعال‌اند. شمارش فهرست بعد از فیلتر درست است. تاریخ پایان با locale/تهران نمایش داده می‌شود؛ مدرکِ approved با تاریخ گذشته در UI expired نشان داده می‌شود، بدون تغییر وضعیت ذخیره‌شدهٔ سرور.

اعتبارسنجی metadata فایل با سقف دقیق۵×۱۰۲۴×۱۰۲۴ بایت و JPEG/PNG/WebP/PDF قرارداد فعلی سرور هماهنگ است. خواندن محتویات/تصویر در کلاینت انجام نمی‌شود؛ بررسی magic bytes و پیکسل همچنان با سرویس سرور است. خطای فایل خالی، بزرگ و نوع نامعتبر، aria-invalid و aria-errormessage دارد. ارسال بدون فایل نیز پیام محلی، فوکوس روی input واقعی و وضعیت invalid دارد؛ پس از انتخاب مجاز، خطا و customValidity پاک می‌شوند.

پوشش دیداری انتخاب فایل با متن فارسی/انگلیسی ساخته شد؛ input واقعیِ focusable با opacity صفر روی آن است و wrapper focus-within دارد. input مخفی display:none نیست و required مرورگر حفظ شده است. نام فایل با bdi از متن جهت دیگر جداست. برای تغییر فایل، همان chooser واقعی به کار می‌رود؛ کنترل جایگزین نمایشیِ بدون رفتار نیست. دکمه‌های پیش‌نمایش نام مدرک را در aria-label دارند و حداقل۴۴px ارتفاع دارند؛ موفقیت پیش‌نمایش فایل واقعی این بار پذیرفته نشده است.

دسترسی مدارک از shortcut خانه اضافه شد و Home→Documents واقعاً با صفحه‌کلید طی شد. جداکنندهٔ اضافهٔ خدماتِ بدون تاریخ در خانه هم با همان الگوی filter/join حذف شد. کارت‌های club/coach، جزئیات باشگاه، Kit و CSS عمومی عوض نشدند؛ guard۵۹ فایل پاس است.

## دادهٔ آزمایشی و حدود امنیت

fixture فقط‌خواندنی دو حالت opt-in دارد: `documents-read` فقط مسیر دقیق GET مدارک را با یک DTO مصنوعی پاسخ می‌دهد و `documents-read-error` همان query را503 می‌کند. در حالت پیش‌فرض populated، مدارک و preview خصوصی401 هستند؛ profile/auth و تمام مسیرهای حساب دیگر نیز401 می‌مانند. در opt-in نیز preview401 است و هیچ URL خصوصی ساختگی تولید نشد. همهٔ نوشتن‌ها پیش از route405 می‌گیرند، Cookie صادر نمی‌شود و بدنه/فایل ذخیره یا لاگ نمی‌شود. این شبیه‌سازیِ دادهٔ query است، نه ورود موفق یا آزمون نقش‌ها.

فرمان fixture از apps/api با runtime نصب‌شده:

```sh
GYM_WEB_READ_FIXTURE=true WEB_READ_PORT=7488 WEB_READ_SCENARIO=documents-read \
NODE_OPTIONS=--max-old-space-size=96 \
node --import tsx ../../apps/application/scripts/web-read-fixture.mts
```

خروجی `.next-qa` با API_URL7488 ساخته شده است؛ اتصال مجدد به API واقعی rebuild با URL صحیح می‌خواهد. شبیه‌ساز و فایل‌های synthetic زیر test/scripts و `.artifacts` هستند؛ فایل جدید واقعی در کاتالوگ یا S3 seed نشد.

## شواهد

۲۸ آزمون در یک اجرای ترتیبی با heap۱۲۸MiB و test-concurrency=1، حدود۵۷۵ms پاس شدند:۱۱ رگرسیون انتخاب سانس/بسته،۵ آزمون metadata/انقضای مدرک و۱۲ آزمون HTTP fixture. موارد تازهٔ HTTP،401 پیش‌فرض مدارک، DTO opt-in بدون مجوز preview/profile،405 نوشتن و تفاوت503 با لیست خالی را تأیید کردند. این تعداد، آزمون PostgreSQL یا آپلود محتوا نیست.

[ماتریس نهایی](documents-web-matrix-2026-10-18.json) شامل۳۶ مورد یکتا است: خدمت نیازمند مدرک/خدمت بدون نیاز/کل تاریخچه × دو زبان × دو تم × سه عرض۳۶۰/۳۹۰/۴۳۰. همه یک main فعال، بدون سرریز، فرم فقط برای خدمت نیازمند، empty درست، وضعیت expired و هدف پیش‌نمایش با ارتفاع حداقل۴۴px داشتند. ماتریس DOM است، نه مرور تصویری تک‌تک موارد یا پذیرش WCAG/صفحه‌خوان.

از طریق chooser واقعی چهار فایل مصنوعی انتخاب شدند: text، PDF صفر بایتی، PDF با۵MiB+۱بایت و PDF بسیار کوچک. سه مورد اول پیام متمایز و ارسال غیرفعال داشتند؛ PDF کوچک فقط metadata معتبر داشت و خطا را پاک کرد، اما محتوا parse/ارسال نشد. پس از فارسی‌سازی picker، text و PDF کوچک دوباره بررسی شدند. پس از اصلاح required، Send بدون فایل در فارسی پیام «یک فایل انتخاب کنید»، aria-invalid=true، error مرتبط، فوکوس روی input و دکمهٔ غیرفعال داشت؛ انتخاب PDF خطا را پاک و دکمه را فعال کرد. FileList metadata در evaluate ابزار نمایان نشد؛ نام/حجمِ مشاهده‌نشده از آن API ادعا نمی‌شود. حجم فایل‌های مصنوعی در فایل‌سیستم معلوم و پیام UI مستقل ثبت شد.

قبل از handler required، browser message انگلیسی در آزمون انگلیسی دیده شد و aria-invalid همچنان false بود. handler تازه علاوه بر ترجمه، وضعیت invalid را پس از اقدام کاربر درست می‌کند. هیچ دکمهٔ Submit با فایل معتبر کلیک نشد. کلمهٔ «پاس» برای اعتبارسنجی/انتخاب فایل است، نه ذخیرهٔ موفق.

ESLint هشت فایل با heap۲۵۶MiB پاس شد. buildها ترتیبی بودند؛ دو بازسازی بعدی به‌دلیل یافتهٔ واقعیِ متن native picker و required انجام شدند. build نهایی یک worker/heap۵۱۲MiB/cache خاموش داشت: compile۹٫۵s، TypeScript۲٫۲s و۶۴ صفحه. پیش‌نمایش۲۵۶MiB و fixture۹۶MiB فقط بعد از build روشن شدند. اجرای اول fixture از root نتوانست tsx را resolve کند؛ با cwd صحیح API و بدون نصب dependency اجرا شد. formatter یک بار از cwd فاقد prettier اجرا نشد؛ مسیر نصب‌شدهٔ root استفاده شد. هیچ فرایند یا فایل پروژهٔ دیگری پاک نشد؛ فضای آزاد ابتدای برش حدود۸۲۴MiB بود و buildهای QA قدیمی در مجموع تنها۲۶MiB بودند، پس حذف نشدند.
