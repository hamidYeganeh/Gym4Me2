# قرارداد و صفحه‌بندی مکان PH1 — ۱۸ اکتبر ۲۰۲۶

T020-a پذیرفته شد: مکان‌ها پس از سقف قبلی از API و کلاینت واقعی قابل دریافت‌اند. T020 والد، پذیرش کامل PH0/PH1، دستگاه و بازیابی مستقل همچنان بازند.

## مشکل و تغییر

API جغرافیا فقط۳۰۰ کشور یا۱۰۰۰ استان/شهر/ناحیه را برمی‌گرداند و راهی برای دریافت ادامه نداشت. اکنون مسیرهای عمومی و ادمین `locations/:kind` صفحهٔ معتبر۱تا۱۰۰۰۰۰، offset و ترتیب نام/شناسه دارند. اندازهٔ قبلی صفحه حفظ شده است؛ parent معتبر و مجوز ادمین همچنان لازم‌اند. parent ناشناخته، صفحهٔ خالی می‌دهد. Swagger پارامترها، حدود، ترتیب، اندازه و پاسخ آرایه را توضیح می‌دهد.

`LocationFiltersDto` و متد `locationPage` در دو کلاینت عمومی/ادمین، یک صفحه را می‌خوانند. متدهای `locations` که انتخاب‌گرهای فعلی استفاده می‌کنند، همهٔ صفحه‌ها را به‌ترتیب جمع می‌کنند؛ هم‌زمان درخواست جدید نمی‌سازند. خطای صفحهٔ بعد به نتیجهٔ موفقِ ناقص تبدیل نمی‌شود. لغو پیش از درخواست/میان صفحه‌ها، درخواست بعدی را متوقف می‌کند. شکل نامعتبر پاسخ، بیش‌بودن تعداد صفحه و شناسهٔ تکراری رد می‌شوند. صفحهٔ آخرِ کاملاً پر یک درخواست خالی اضافه نیاز دارد.

کلیدهای کش همچنان parent و محدودهٔ host/app/locale/session را حفظ می‌کنند. UI انتخاب‌گر و طراحی محافظت‌شده تغییر نکردند. صفحه‌بندی offset snapshot نیست؛ تغییر هم‌زمان داده ممکن است مرز صفحه‌ها را جابه‌جا کند. در حالت شناسهٔ تکراری، کلاینت خطا می‌دهد تا فهرست ناقص را موفق نشان ندهد.

[قرارداد API](../api-conventions.md) نیز به مسیرها و ساختار واقعاً پیاده‌شده به‌روز شد؛ ادعای قدیمی «فقط health پیاده است» حذف شد.

## شاهد و محدوده

ابتدا کد/آزمون نوشته و سپس checks اجرا شدند. فقط API آزمایشی و یک فرایند Node محدود برای خواندن کلاینت واقعی روی loopback اجرا شدند؛ وب/native یا سرویس اصلی اجرا/rebuild نشد.

| بررسی | نتیجه |
| --- | --- |
| Jest کاتالوگ با PostgreSQL/S3 واقعی، یک پردازش، heap۶۴۰MiB | ۴۱/۴۱، نهایی۱۰٫۳۷۷ثانیه |
| آزمون‌های مشترک کلاینت، یک پردازش، heap۱۹۲MiB | ۲۳/۲۳؛ شامل۹ آزمون تازهٔ مکان |
| قرارداد باشگاه و localization با `--watchman=false` | ۱۱/۱۱ |
| types API، کلاینت و UI | exit0؛ سقف heap۶۴۰/۳۸۴/۷۶۸MiB |
| lint API و فایل‌های مرتبط کلاینت/آزمون | exit0 |

دادهٔ مصنوعی شامل۳۰۱ کشور و۱۰۰۱ مورد در هر سطح استان/شهر/ناحیه بود؛ جمع۳۳۰۴ رکورد. کشورهای قبلی fixture نیز در نتیجه حضور داشتند. برای هر چهار نوع و هر دو مسیر عمومی/ادمین، دو صفحهٔ بدون تکرار و با ترتیب مورد انتظار، پایان خالی، والد خارجی، ورودی نامعتبر و منع نشست بیزینس روی admin بررسی شد. OpenAPI واقعی نیز حدود page و پاسخ array را داشت.

سپس API تست با پورت تصادفی روی `127.0.0.1` گوش داد؛ probe جدا، `catalogClients` و `adminClients` واقعی ESM را از `packages/api` بار کرد و با `createApiClient` و fetch واقعی همهٔ صفحه‌ها را گرفت. هر دو فهرست یکسان داشتند: کشورها۳۰۲ و هر سطح دیگر۱۰۰۱؛ `locationPage` صفحهٔ دوم شهر را۱ و صفحهٔ سوم ناحیه را۰ دریافت کرد. cookie مصنوعی ادمین فقط در محیط فرایند بود؛ خروجی probe فقط شمار رکورد داشت.

آزمون‌های کلاینت علاوه بر مسیر/parent/header و درخواست ترتیبی، فهرست خالی، صفحهٔ آخر دقیقاً پر، شکست صفحهٔ بعد، لغو، پاسخ نامعتبر و تکرار صفحه را پوشش دادند. این‌ها بررسی DOM انتخاب‌گر، صفحه‌خوان یا دستگاه واقعی نیستند.

اجرای نخست unit به Watchman خارج sandbox دسترسی نداشت؛ نتیجهٔ آن برای پذیرش شمرده نشد. اجرای صریح بدون Watchman موفق بود. کاتالوگ پیش از اضافه‌شدن probe نیز۴۱/۴۱ پاس شد؛ شاهد نهایی مربوط به اجرای دارای probe است.

## پاک‌سازی و ادامه

دیتابیس مستقل `gym4me_ph1geo_1a14e17_test` و bucket تصادفی تست استفاده شدند. teardown موفق bucket/objectها را پاک و API را بست؛ دیتابیس نیز DROP شد. دادهٔ اصلی، containerهای قبلی و انتشار بیرونی تغییر نکردند. logها در `.artifacts/ph1-location-pages-2026-10-18/` هستند.

پذیرش کامل T020 به ممیزی باقی قراردادها/حالت‌های واقعی نیاز دارد؛ این برش به جغرافیا محدود است. PH0 به ماتریس کامل ظاهر/حرکت/دسترس‌پذیری و دستگاه نیاز دارد؛ PH1 نیز کاتالوگ واقعی وب/native و عملیات مستقل را در backlog نگه می‌دارد. کاربر مقصد بکاپ خارجی فعلاً ندارد.
