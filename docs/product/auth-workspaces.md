# ورود، حساب و پنل‌های Gym4Me

پیاده‌سازی مرحله اول هویت و فضای کاری — ۱۹ مهر ۱۴۰۵ / 2026-10-11.

یک ردیف `users` برای هر شماره موبایل داریم. اپ مربی و ورزشکار مشترک است؛ ورود به Business یا Admin حساب دیگری ایجاد نمی‌کند. هر سطح نشست مستقل دارد و مجوزها در سرور بررسی می‌شوند.

## تنظیم کاوه‌نگار

در `apps/api/.env`:

```dotenv
AUTH_SECRET=<random-secret-at-least-32-characters>
KAVENEGAR_API_KEY=<your-kavenegar-key>
KAVENEGAR_OTP_TEMPLATE=g4m-otp
AUTH_APPLICATION_ORIGIN=http://localhost:7081
AUTH_BUSINESS_ORIGIN=http://localhost:7083
AUTH_ADMIN_ORIGIN=http://localhost:7082
```

برای secret جدید از `openssl rand -hex 32` استفاده کنید. در محیط توسعه فعلی secret تصادفی در فایل نادیده‌گرفته‌شدهٔ `.env` ساخته شده است؛ کلید کاوه‌نگار هنوز باید توسط صاحب پروژه وارد شود. مقدار secret را بین instanceهای یک محیط یکسان نگه دارید. هیچ کلید واقعی در مخزن قرار نمی‌گیرد.

در پنل کاوه‌نگار یک الگوی Verify Lookup به نام `g4m-otp` با متغیر `%token` تعریف و تأیید کنید؛ متن پیشنهادی:

```text
کد ورود جیم‌فورمی: %token
اعتبار: ۲ دقیقه
این کد را در اختیار دیگران قرار ندهید.
```

Adapter از `POST /v1/{key}/verify/lookup.json` و پارامترهای `receptor`، `token`، `template` و `type=sms` استفاده می‌کند. برای استفاده از Verify Lookup، سرویس مربوط باید در حساب کاوه‌نگار فعال باشد. مرجع: [مستند رسمی کاوه‌نگار](https://kavenegar.com/rest.html#verifylookup).

در صورت نبود کلید یا خطای ارائه‌دهنده، پاسخ 503 خوانا برمی‌گردد. هیچ کد ثابت، bypass ورود یا چاپ OTP در لاگ وجود ندارد. تست‌ها adapter را جایگزین می‌کنند و پیامک واقعی نمی‌فرستند. بعد از تغییر `.env`، API را دوباره اجرا کنید. ارسال واقعی پس از افزودن کلید و تأیید الگو باید بررسی شود.

## رفتار ورود

1. شماره‌های فارسی/عربی، `09…`، `+989…` و `00989…` به `+989…` تبدیل می‌شوند.
2. کد تصادفی پنج‌رقمی با اعتبار ۱۲۰ ثانیه ساخته می‌شود؛ فقط HMAC آن در پایگاه داده می‌ماند.
3. فاصله ارسال مجدد ۶۰ ثانیه، سقف ارسال ۵ درخواست برای هر شماره در ساعت و ۳۰ درخواست برای هر IP در ساعت است. محدودیت‌ها در PostgreSQL و بین instanceها مشترک‌اند.
4. حداکثر پنج تلاش اشتباه؛ هر کد یک‌بار مصرف است. ارسال مجدد کد قبلی را باطل می‌کند. کد ارسال‌نشده قابل استفاده نیست.
5. تأیید موفق حساب را ایجاد/بازیابی و کوکی HttpOnly صادر می‌کند. پاسخ شامل توکن نیست.
6. کوکی‌ها host-only و SameSite=Strict هستند؛ در production گزینه Secure فعال است. نشست ادمین ۸ ساعت و نشست اپ/بیزینس ۳۰ روز اعتبار دارد. تمدید خودکار فعلاً وجود ندارد.
7. خروج و لغو نشست در دیتابیس اعمال می‌شوند. تعلیق کاربر، تمام نشست‌های او را باطل می‌کند؛ فعال‌سازی مجدد نشست قبلی را زنده نمی‌کند.

تمام مسیرهای هویت و پنل‌ها نیازمند `x-gym-client: application|business|admin` و مبدأ منطبق‌اند. مرورگر برای GET ممکن است Origin نفرستد؛ در این حالت Referer معتبر بررسی می‌شود. ابزارهای API باید Origin متناسب با پنل را ارسال کنند. انتخاب header هیچ نقشی به حساب نمی‌دهد. پاسخ‌ها `Cache-Control: no-store` دارند.

در production برای هر پنل دامنه HTTPS مستقل تنظیم کنید و `CORS_ORIGINS` را نیز هماهنگ نگه دارید. این نسخه عمداً `X-Forwarded-For` نامطمئن را قبول نمی‌کند؛ اگر API پشت reverse proxy اجرا می‌شود، پیکربندی trusted proxy و محدودیت نرخ لبه باید پیش از انتشار تنظیم و تست شود؛ وگرنه کاربران proxy یک سهمیه IP مشترک خواهند داشت.

## مسیرهای API

پیشوند همه مسیرها `/api/v1` است؛ مسیرهای محصول با `auth`، `profile`، `business` و `admin` نام‌گذاری شده‌اند. نام‌های `identity` و مشابه برای این APIها استفاده نمی‌شوند.

| متد | مسیر | کاربرد |
| --- | --- | --- |
| POST | `/auth/otp/request` | دریافت کد؛ بدنه `phone` |
| POST | `/auth/otp/verify` | تأیید؛ بدنه `challengeId`, `code` |
| GET | `/auth/sessions` | نشست‌های فعال حساب بدون اطلاعات محرمانه |
| POST | `/auth/sessions/logout` | خروج از نشست جاری |
| POST | `/auth/sessions/:id/revoke` | پایان یکی از نشست‌های خود |
| GET / PATCH | `/profile/account` | مشاهده حساب / ویرایش `displayName` |
| GET | `/profile/access` | مجموعه‌ها و نقش‌ها و وضعیت دسترسی ادمین |
| GET | `/profile/invitations` | دعوت‌های معتبر همین شماره |
| POST | `/profile/invitations/:id/accept` | پذیرش دعوت |
| GET / POST | `/business/organizations` | مجموعه‌های خود / ساخت مجموعه |
| GET / POST | `/business/organizations/:organizationId/branches` | شعب مجموعه / ساخت شعبه |
| GET | `/business/organizations/:organizationId/team` | اعضا و دعوت‌های باز، فقط مالک |
| POST | `/business/organizations/:organizationId/invitations` | دعوت با `phone`, `role` |
| POST | `/business/organizations/:organizationId/invitations/:id/revoke` | لغو دعوت |
| POST | `/business/organizations/:organizationId/team/:id/remove` | حذف دسترسی همکار، به‌جز مالک |
| GET | `/admin/overview` | شمارش واقعی کاربران، مجموعه‌ها و موارد در انتظار |
| GET | `/admin/users?search=&page=1` | جست‌وجوی کاربران؛ ۲۵ ردیف در هر صفحه |
| PATCH | `/admin/users/:id/status` | `active` یا `suspended` با `reason` |
| GET | `/admin/organizations?status=pending&page=1` | صف بررسی مجموعه‌ها |
| POST | `/admin/organizations/:id/review` | `approved`, `rejected`, `suspended` با `reason` |
| GET | `/admin/audit?page=1` | سابقه تصمیم‌ها، فقط خواندنی |

Swagger: `/api/v1/system/docs`. بدنه‌ها strict validation دارند؛ ارسال فیلدهایی مثل role در پروفایل یا درخواست OTP رد می‌شود. خطاهای ورودی 400، ورود 401، مجوز/مبدأ 403، منبع ناموجود 404، تعارض 409، محدودیت نرخ 429 و اختلال SMS 503 هستند.

## مدل‌ها

| جدول | فیلدهای اصلی و مسئولیت |
| --- | --- |
| `users` | `id`, `phone` یکتا، `displayName`, `status`, `phoneVerifiedAt`, زمان ساخت/ویرایش |
| `otp_challenges` | شماره، سطح ورود، HMAC کد، تعداد تلاش، زمان ارسال/انقضا/مصرف |
| `auth_rate_limits` | کلید HMAC شماره/IP، شمارنده و انقضای پنجره محدودیت |
| `auth_sessions` | کاربر، سطح ورود، hash توکن تصادفی، شرح دستگاه، زمان ساخت/انقضا/لغو |
| `organizations` | نام، slug یکتا، وضعیت بررسی، دلیل بررسی، زمان‌ها |
| `branches` | مجموعه والد، نام، slug یکتا در مجموعه، منطقه زمانی |
| `organization_members` | عضویت کارکنان، `organizationId + userId` یکتا، نقش؛ مستقل از عضویت پولی ورزشکار |
| `organization_invitations` | مجموعه، شماره، نقش پیشنهادی، دعوت‌کننده، انقضا، زمان پذیرش/لغو |
| `platform_admins` | مجوز مدیریت پلتفرم مستقل از نقش باشگاه |
| `audit_events` | عامل، مجموعه، نوع اقدام، هدف، جزئیات محدود و زمان |

ساخت مجموعه و مالکیت در یک transaction انجام می‌شود. دعوت فقط به شماره تأییدشده همان حساب تعلق دارد، هفت روز معتبر است و دعوت جدید همان شماره در همان مجموعه، دعوت قبلی را لغو می‌کند. دعوت در پنل قابل مشاهده است؛ ارسال SMS دعوت در این برش پیاده نشده است. حذف همکار روی درخواست بعدی اثر می‌گذارد.

## ماتریس دسترسی این نسخه

این جدول تاریخیِ برش اولیه است. نقش‌های محدود به شعبه بعداً اضافه شدند؛ مرجع جدید [ماتریس PH1](access-matrix.md) است. نتیجهٔ آزمون هر برش در گزارش همان تاریخ ثبت می‌شود.

| عمل | حساب عادی | مالک | مدیر مجموعه | پذیرش / حسابدار | ادمین پلتفرم |
| --- | --- | --- | --- | --- | --- |
| پروفایل و نشست‌های خود | بله | بله | بله | بله | بله |
| ساخت مجموعه در بیزینس | بله | بله | بله | بله | فقط با ورود بیزینس |
| مشاهده شعب مجموعه مرتبط | خیر | بله | بله | بله | مجوز خودکار ندارد |
| ساخت شعبه مرتبط | خیر | بله | بله | خیر | مجوز خودکار ندارد |
| دعوت، مشاهده تیم و لغو دسترسی | خیر | بله | خیر | خیر | مجوز خودکار ندارد |
| کاربران پلتفرم و بررسی مجموعه‌ها | خیر | خیر | خیر | خیر | فقط نشست ادمین |

نقش‌ها در این نسخه در سطح مجموعه‌اند. محدودکردن کارکنان به شعب مشخص، نقش‌های مالی عملیاتی، نقش مربی حرفه‌ای و انتقال مالکیت هنوز پیاده نشده‌اند. وضعیت تأیید مجموعه از ویرایش اطلاعات داخلی آن جداست؛ سرویس عمومی کاتالوگ/فروش هنوز ساخته نشده تا از وضعیت تأیید برای انتشار استفاده کند.

## صفحات

- اپ مشترک: `/login`, `/profile`, `/sessions`, `/invitations`؛ تجربه کشف موجود حفظ شده است.
- بیزینس: `/`, `/login`, `/organizations`, `/branches`, `/team`, `/profile`, `/sessions`, `/invitations`.
- ادمین: `/`, `/login`, `/users`, `/organizations`, `/audit`, `/profile`, `/sessions`, `/invitations`.

حالت بارگذاری، داده خالی، خطای شبکه، خطای اعتبارسنجی، نبود دسترسی و موفقیت در صفحات وجود دارد. زبان این صفحات فارسی و جهت RTL است. برای لغو دسترسی تیم و تصمیم ادمین، پنجره تأیید وجود دارد. اعداد داشبورد از API می‌آیند و داده نمایشی به‌عنوان داده واقعی ارائه نمی‌شود.

مرجع طراحی ورود: [Sweatpals در Mobbin](https://mobbin.com/flows/f47b33c2-0eaa-458d-a6c6-6ccfed1f8b2a). فرم تلفن، مرحله جداگانه تأیید و ارسال مجدد زمان‌دار با کامپوننت‌های موجود shadcn پروژه بازسازی شده‌اند.

## فعال‌سازی اولین ادمین

ابتدا با شماره واقعی وارد شوید تا حساب تأیید شود، سپس اپراتور مجاز سرور اجرا کند:

```sh
pnpm --filter api admin:grant 09123456789
```

اسکریپت فقط به حساب فعال و تأییدشده دسترسی می‌دهد و رویداد ثبت می‌کند. هیچ کاربر اول، شماره ثابت یا فرم عمومی نمی‌تواند خودش ادمین شود. حساب‌های ادمین از مسیر تعلیق کاربران قابل تعلیق نیستند. به‌جای ساخت حساب نمایشی دائمی، برای UI فقط fixture موقت استفاده و سپس حذف شد.

## اجرا و بررسی

```sh
pnpm db:up
pnpm --filter api db:migrate
pnpm dev
pnpm db:test:up
pnpm --filter api test --runInBand
pnpm --filter api test:e2e --runInBand
pnpm --filter api test:auth
pnpm --filter api test:db
```

`test:auth` فقط دیتابیسی با پسوند `_test` را می‌پذیرد؛ از PostgreSQL و HTTP واقعی با adapter پیامک جایگزین‌شده استفاده می‌کند. برای بازنشانی دیتابیس اصلی یا ایجاد ادمین خودکار استفاده نمی‌شود.

## ادامه فاز ۱

این برش، پایه وب احراز هویت و پنل‌ها را تحویل می‌دهد؛ پایان تمام PH1 نیست. موارد باقی‌مانده: ذخیره امن نشست و اتصال API در build بومی Capacitor، تغییر شماره، نقش محدود به شعبه، ویرایش اطلاعات کامل مجموعه/شعبه، مدارک و فایل، رضایت/حذف/خروجی داده، کاتالوگ عمومی، انتخاب حالت مربی پس از احراز صلاحیت، پاک‌سازی دوره‌ای challenge/sessionهای منقضی، تنظیم proxy و محدودیت‌های لبه، آزمایش SMS واقعی و تست انتشار. رزرو، پرداخت، برنامه تمرینی و تجهیزات مربوط به فازهای بعدند.

## نتیجه بررسی این تغییر

- ۴۴ تست پاس شد: ۱۱ تست واحد (config، نرمال‌سازی و adapter کاوه‌نگار)، ۱۱ تست قرارداد API، ۱۸ تست HTTP با PostgreSQL برای OTP و دسترسی، ۴ تست migration و یکپارچگی دیتابیس.
- build تولیدی API و هر سه frontend موفق شد؛ TypeScript سه اپ و بسته UI و lint کدهای جدید بررسی شد.
- در مرورگر: ثبت مجموعه، افزودن شعبه، بررسی مجموعه توسط ادمین، نمایش نتیجه و ثبت audit روی داده موقت محلی بررسی شد. حساب، نشست‌ها و داده‌های موقت پس از تست پاک شدند.
- ارسال زنده کاوه‌نگار و ورود نسخه بومی هنوز در این نتیجه آزمون نیستند.

## گسترش مدل مجموعه به باشگاه

مدل کاتالوگ در [club-catalog.md](club-catalog.md) اضافه شده است. ساخت مجموعه از مسیر قبلی بیزینس اکنون Club و شعبهٔ اصلی را نیز در همان تراکنش می‌سازد؛ شناسه‌های قبلی حفظ می‌شوند. نتیجهٔ بررسی ادمین روی امکان انتشار اثر دارد، ولی تأیید به‌تنهایی منتشر نمی‌کند. قرارداد جدید، مرجع فیلدها و اجباری‌بودن اطلاعات باشگاه است.
